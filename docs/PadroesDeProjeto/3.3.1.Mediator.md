# 3.3.1 Mediator

## 1. Visão Geral

O **Mediator** é um padrão de projeto **comportamental**, catalogado pela **Gang of Four (GoF)**, que permite reduzir as dependências caóticas entre objetos. O padrão restringe comunicações diretas entre objetos e os força a colaborar apenas através de um objeto mediador **([GAMMA et al., 1995](https://www.javier8a.com/itc/bd1/articulo.pdf))**.

Em vez de os componentes se comunicarem diretamente entre si, eles enviam notificações a um mediador central, que redireciona as chamadas para os componentes apropriados.
Isso reduz o acoplamento do sistema, facilita a manutenção e evita a proliferação de dependências cruzadas entre classes ([REFACTORING.GURU, 2026](https://refactoring.guru/pt-br/design-patterns/mediator)).

## 3. Aplicabilidade

O padrão **Mediator** pode ser utilizado em várias situações, sendo algumas das mais comuns ([REFACTORING.GURU, 2026](https://refactoring.guru/pt-br/design-patterns/mediator)):

### 3.1. Quando é difícil mudar algumas classes porque estão firmemente acopladas a várias outras

O Mediator permite extrair todas as relações entre classes para uma classe separada, isolando quaisquer mudanças para um componente específico do resto dos componentes.

### 3.2. Quando um componente não pode ser reutilizado por ser muito dependente de outros

Após aplicar o Mediator, os componentes individuais tornam-se alheios uns aos outros. Eles ainda podem se comunicar, mas de forma indireta, por meio do objeto mediador. Para reutilizar um componente em outra aplicação, basta fornecer a ele uma nova classe mediadora.

### 3.3. Quando são criadas muitas subclasses apenas para reutilizar comportamento básico em vários contextos

Como todas as relações entre componentes ficam contidas dentro do mediador, é fácil definir novas formas de colaboração introduzindo novas classes mediadoras, sem alterar os próprios componentes.

## 4. Prós

- Segue o **Princípio da Responsabilidade Única**, centralizando as comunicações entre vários componentes em um único lugar, tornando-as mais fáceis de entender e manter.
- Segue o **Princípio Aberto/Fechado**, permitindo introduzir novos mediadores sem ter que alterar os próprios componentes.
- Reduz o acoplamento entre os vários componentes de um programa.
- Facilita a reutilização de componentes individuais em contextos diferentes.

## 5. Contras

- Com o tempo, o mediador pode evoluir para um **Objeto Deus** — uma classe que acumula responsabilidades demais e se torna difícil de manter.
- Pode introduzir complexidade adicional, especialmente em sistemas pequenos onde o acoplamento direto seria suficiente.
- Exige conhecimento de interfaces e delegação de eventos, o que pode dificultar a compreensão para iniciantes.

## 6. Implementação

### 6.1. Senso Crítico

No contexto do **FCTE Hoje**, a aplicação do padrão GoF Mediator mostrou-se adequada para coordenar a **tela de publicação de conteúdo**, utilizada pelo `Publicador` para criar uma nova **Notícia**, **Evento**, **Edital** ou **Cardápio do RU**. O objetivo central foi desacoplar os componentes da interface (campo de conteúdo, seletor de tipo, botões de publicar e cancelar) e centralizar em um único ponto a lógica de validação do formulário, habilitação do botão de envio e disparo da publicação.

Essa escolha se conecta diretamente com os demais padrões do projeto: o **Factory** ([3.1.2](3.1.2.Factory.md)) é o responsável por instanciar o `Conteudo` específico após o clique no botão `Publicar`, e o `Publicador` — cliente do Factory — armazena o conteúdo gerado. O Mediator atua estritamente no nível de **coordenação da UI**, sem se sobrepor à responsabilidade do **Proxy** ([3.2.4](3.2.4.Proxy.md)), que cuida do controle de acesso do `Publicador` antes da publicação.

Neste diagrama, a **Interface Mediadora** `Mediator` declara o método `notify()` utilizado pelos componentes para comunicar eventos. A **Classe Mediadora Concreta** `PublicacaoDialog` implementa essa interface e centraliza as regras da tela (validar formulário, habilitar/desabilitar o `BotaoPublicar`, disparar a publicação ou limpar o formulário). A **Classe Base** `Component` mantém uma referência ao mediador e delega eventos a ele. Os **Componentes Concretos** `CampoConteudo`, `SeletorTipo`, `BotaoPublicar` e `BotaoCancelar` estendem `Component` e se comunicam exclusivamente por meio do mediador, sem dependências diretas entre si.

### 6.3. Código

A implementação a seguir aplica o padrão **Mediator** ao módulo de **publicação de conteúdo do FCTE Hoje**. O `PublicacaoDialog` atua como mediador concreto, centralizando a coordenação entre o `CampoConteudo` (texto da publicação), o `SeletorTipo` (Notícia / Evento / Edital / Cardápio RU), o `BotaoPublicar` e o `BotaoCancelar`, de modo que esses componentes não se comuniquem diretamente entre si.

#### 6.3.1 Mediator (Interface)

```python
from abc import ABC, abstractmethod


class Mediator(ABC):

    @abstractmethod
    def notify(self, sender: "Component", event: str) -> None:
        """Recebe e roteia eventos emitidos por um Component."""
        pass
```

#### 6.3.2 Component (Classe Base)

```python
class Component:
    def __init__(self, mediator: Mediator = None):
        self._mediator = mediator

    def set_mediator(self, mediator: Mediator) -> None:
        self._mediator = mediator
```

#### 6.3.3 Concrete Components

```python
class CampoConteudo(Component):
    def __init__(self, mediator: Mediator = None):
        super().__init__(mediator)
        self.texto: str = ""

    def digitar(self, texto: str) -> None:
        self.texto = texto
        print(f"[CampoConteudo] Texto atual: '{self.texto}'.")
        self._mediator.notify(self, "input_change")


class SeletorTipo(Component):
    TIPOS_VALIDOS = ("Noticia", "Evento", "Edital", "CardapioRU")

    def __init__(self, mediator: Mediator = None):
        super().__init__(mediator)
        self.tipo: str = ""

    def selecionar(self, tipo: str) -> None:
        if tipo not in self.TIPOS_VALIDOS:
            print(f"[SeletorTipo] Tipo '{tipo}' inválido.")
            return
        self.tipo = tipo
        print(f"[SeletorTipo] Tipo selecionado: {tipo}.")
        self._mediator.notify(self, "tipo_selecionado")


class BotaoPublicar(Component):
    def clicar(self) -> None:
        print("[BotaoPublicar] Clique no botão de publicar.")
        self._mediator.notify(self, "publicar")


class BotaoCancelar(Component):
    def clicar(self) -> None:
        print("[BotaoCancelar] Clique no botão de cancelar.")
        self._mediator.notify(self, "cancelar")
```

#### 6.3.4 Concrete Mediator

```python
class PublicacaoDialog(Mediator):
    def __init__(self):
        self.campoConteudo = CampoConteudo(self)
        self.seletorTipo = SeletorTipo(self)
        self.okBtn = BotaoPublicar(self)
        self.cancelBtn = BotaoCancelar(self)

    def notify(self, sender: Component, event: str) -> None:
        if event in ("input_change", "tipo_selecionado"):
            self._validar_formulario()
        elif event == "publicar":
            self._publicar()
        elif event == "cancelar":
            self._cancelar()

    def _validar_formulario(self) -> None:
        if self.campoConteudo.texto and self.seletorTipo.tipo:
            print("[Mediator] Formulário válido — botão Publicar habilitado.")
        else:
            print("[Mediator] Formulário incompleto — botão Publicar desabilitado.")

    def _publicar(self) -> None:
        if not self.campoConteudo.texto or not self.seletorTipo.tipo:
            print("[Mediator] Publicação bloqueada: preencha conteúdo e tipo.")
            return
        print(
            f"[Mediator] Publicando {self.seletorTipo.tipo}: "
            f"\"{self.campoConteudo.texto}\""
        )

    def _cancelar(self) -> None:
        self.campoConteudo.texto = ""
        self.seletorTipo.tipo = ""
        print("[Mediator] Publicação cancelada. Formulário limpo.")
```
